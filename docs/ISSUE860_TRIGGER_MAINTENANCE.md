# 최초 writer gate 전환: 트리거 중지·복원 도구 (staged)

이 변경은 #860 안전 전환의 **트리거 단계만** 구현한다. 배포를 허가하거나
`GAS_FIRST_GATE_CUTOVER_UNVERIFIED`를 해제하지 않는다. 운영 자동화는 아직 중지하지 않는다.
사용자는 일시 중지→배포→검증→재개를 승인했지만 운영 증빙을 대신할 수는 없다.

후속 통합 경로는 [최초 전환 절차](ISSUE860_FIRST_CUTOVER.md)를 따른다. staged 파일을
단독 설치하는 대신 정확히 고정된 유지보수 프로필의 동일 SERVER_JS 안에 합친다.
일반 배포 차단은 그대로이며, 전체 절차와 독립 운영 증빙 없이는 실행하지 않는다.

## 확인한 범위

2026-11-04 Apps Script UI에서 소유 계정의 설치형 트리거 11개를 확인했다.
배포 열은 Head 5개 / v336 6개로 표시됐다. 웹앱만 업데이트한 뒤 모든 트리거가
신규 코드를 실행한다고 가정하지 않는다. 개별 UI 설정과 실제 실행 버전 재확인이 필요하다.
기존 함수의 기본 설치 시각을 현재 트리거의 실제 설정이라고 간주하지 않는다.

`scripts/staged/issue860-trigger-maintenance.gs`는 editor 호출 전용이며
현재 운영 소스·웹/API·메뉴·워크플로에 연결하지 않는다. 일반 deploy는
추가 SERVER_JS 파일과 승인 해시가 다른 소스를 차단하므로 **그대로 업로드하면 안 된다**.
실행하려면 별도 검토된 전체 소스/manifest 및 첫 전환 경로에 통합해야 한다.
따라서 이 PR만 병합해도 운영에 실행 가능한 전환이 생기는 것은 아니다.

## 입력과 상태

운영자가 UI에서 정확한 trigger ID, 함수, 이벤트, 원본 spreadsheet ID,
기존 배포 표시, 주기·KST 시각을 기록한 manifest를 제공한다. 시간 트리거의
주기/시각과 배포 binding은 Trigger API로 읽어 복원할 수 없다. 입력의 `uiEvidence`는
기록 참조일 뿐 설정 정확성·전체 actor 격리의 자동 인증이 아니다.
시간대는 Asia/Seoul, 시간 기반 9개/시트 edit·change 각1개, 총11개만 허용한다.
새로운/중복/누락 함수가 있으면 중지하지 않는다. 실제 ID·원본 시트 ID는 커밋/로그에 넣지 않는다.

1. `issue860PrepareTriggerPause_(manifest)`: 현재 소유 계정의 실제 목록과 ID·함수·이벤트·원본을
   대조하고 Script Properties에 복원 정보를 저장·재조회한다. 삭제하지 않는다.
2. `issue860PausePreparedTriggers_(operationId)`: PREPARED→PAUSING을 먼저 저장·재조회한 뒤
   기록된 ID만 삭제한다. 삭제 중 실패하면 PAUSING 상태와 원본 manifest를 보존한다.
   재시도는 같은 ID 목록의 남은 트리거만 대상으로 하며, 빈 목록 확인 후 PAUSED로 기록한다.
3. 별도 경로에서 모든 계정·구버전·편집기·외부 writer의 유입 차단과 실행 종료,
   정확 후보 소스 게시 및 DRAINING 초기화를 증명해야 한다. **이 도구는 이 단계를 구현하지 않는다.**
4. `issue860RestorePreparedTriggers_(operationId)`: 실제 후보의 gate 상태 검증 함수를 재사용해
   동일 release/DRAINING/active=0일 때만 복원을 시작한다. 기록된 일정과 원본으로
   현재 소스의 HEAD 트리거를 생성한다. 구버전 binding은 재생성하지 않는다.
   각 생성 전 intent와 생성 후 ID를 영속화하고 목록을 독립 재조회한다.
5. 생성 응답 유실 시 pending 함수의 정확히 한 후보만 연결한다. 후보가 없으면
   아직 생성 중일 수 있어 자동 재생성하지 않는다. 둘 이상이면 모호함으로 차단한다.
   격리된 운영자 확인 없이 pending을 지우거나 모르는 트리거를 삭제하지 않는다.
6. 전부 복원 후 RESTORED를 기록한다. **gate는 DRAINING을 유지**한다. 배포/인증/잘못된
   인증 거부/전체 트리거 새 버전 연결을 검증한 별도 경로에서만 재개한다.

ScriptLock은 이 도구의 동시 실행을 직렬화한다. 구버전·타 계정·직접 Sheets writer를
차단한다는 의미가 아니다. getProjectTriggers()는 현재 사용자 소유만 조회하므로
PAUSED도 모든 사용자/모든 writer의 중지 증거가 아니다.

## 실패·복구 경계

- 모든 삭제 전 복원 정보를 보존한다. 부분 삭제·Properties 응답 유실 후 상태를 재조회해 이어간다.
- 삭제·생성 응답 유실을 성공으로 숨기지 않는다. 생성 결과가 불명확하면 자동 중복 생성하지 않는다.
- 같은 일정도 재설치하면 임의 실행 분/다음 실행 시점이 바뀔 수 있다. 정확한 이전 실행 위상을
  복원한다고 주장하지 않는다. 유지보수 중 누락 이벤트는 따로 점검하며 금융 백필을 자동 실행하지 않는다.
- gate 도입 전의 중지 취소·구버전 복원, 도입 이후 전진 복구는 별도 구현/검토가 필요하다.
  이 도구는 운영 중지를 시작하기에 충분한 완성된 cutover가 아니다.
- 저널 삭제·초기화·gate OPEN 전환·수리 승인·금융 원본·Telegram 발송 기능은 없다.
- 전체 소스 통합/독립 리뷰/실운영 증빙 전까지 원래 배포 차단을 유지한다.

## 검증

`node scripts/check-issue860-trigger-maintenance.mjs`가 실제 staged 함수와 실제 후보의
gate 상태 검증 함수를 VM에서 실행한다. 일정 builder 인자, 잠금, journal 선저장,
부분 삭제, 재시도, 생성 응답 유실/불명확, 중복·누락, 잘못된 operation/manifest,
OPEN/active/다른 release 거부, DRAINING 유지와 금융 서비스 무접근을 확인한다.
실제 트리거 변경·배포·웹앱 검증·금융 데이터 검증은 별도 미실행이다.
