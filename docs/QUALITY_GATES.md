# 상시 코드 품질 및 재발 방지 기준

> 적용 범위: 이 저장소의 모든 후속 수정·PR·Codex 리뷰·GAS 운영 변경. 이 문서는 검토 가이드이며, CI 자동 강제 여부는 실제 워크플로 설정으로 별도 확인한다. 일회성 PR #471 전용 문서가 아니다.

## 1. 핵심 목표와 범위 통제

- 버그를 하나 고칠 때 관련 실행 경로의 **안전성(safety: 데이터/상태가 잘못되지 않음)**과 **진행성(liveness: 재시도 기회가 있으면 복구가 결국 진행됨)**을 모두 평가한다.
- 가능하면 하나의 동작 계약 또는 불변조건을 단위로 작은 PR을 구성한다. 임시 패치가 서로 의존하면 공통 원인을 먼저 정리하고, 서로 독립적인 변경까지 한 PR에 넣지 않는다.
- 새 잠금·조건문·재시도·예약·예외 처리를 추가하면 그 제약으로 **기존 작업의 다음 실행 기회가 사라지지 않는지** 반대 방향 경로를 전수 확인한다.
- Codex 리뷰를 설계 검증의 첫 단계로 사용하지 않는다. 먼저 변경 영향도를 파악하고 검증 근거를 구축한다.

## 2. 변경 전 필수 영향 분석

1. 최신 기준 브랜치와 PR HEAD SHA, 열린 PR, 관련 이전 PR 및 실제 운영 배포 버전을 구분한다. 오래되거나 outdated인 리뷰를 신규 미해결 지적으로 중복 처리하지 않는다.
2. 변경 함수만이 아니라 해당 함수의 **모든 호출자/피호출자**, 공통 상태·시트·PropertiesService 키, 다른 계정의 트리거, 예외 및 finally 경로, 수동 실행 진입점을 확인한다.
3. 변경 전 동작 계약을 작성한다: 입력·성공·실패·중복·재시도·부분 완료·다음 실행 기회. 외부 API 실패/데이터 공백의 처리 정책도 명시한다.
4. 재현 가능한 문제라면 **수정 전 실패하는 테스트**를 먼저 추가한다. 재현이 어려우면 왜 어려운지와 대체 검증 방법을 기록한다.

## 2-A. 사전 자체검토 및 교차 운영 영향 검증 (모든 후속 변경 필수)

Codex 리뷰를 받기 전, 단일 함수나 해당 PR의 변경 줄만 보는 검토를 금지한다. 담당자는 다음 **교차 영향 매트릭스**를 실제 동작·상태·호출 관계에 따라 작성하거나, 무관하다는 근거를 적는다.

| 검증 축 | 최소 검토 대상 | 반례 확인 |
| --- | --- | --- |
| 다른 PR·배포 | main, 최근 병합 코드, 진행 중 PR, GAS 운영 버전/실제 트리거 소유자 | 최신 PR만 정상이고 운영 버전·이전 기능과 충돌하는가? |
| 자동 실행 | 19:00 정규 마감, 20:30 watchdog, 22:10 백필, deferred NAV, 수동 실행, Snapshot 복구 | 동일 시트 쓰기·잠금·트리거·예약이 경합하거나 서로의 복구 기회를 없애는가? |
| 데이터 원천 | KRX/해외 종가, Toss·Yahoo, NAV, 가격이력, 거래원장, 과거 수량, 평가금액·손익 | 원천 날짜·휴장·빈 응답·중복/이월·수기값 보호·소급 변경에 영향을 주는가? |
| 상태·표시 | PropertiesService, snapshot 백업·큐·마커, 웹 API, 사용자 UI, 손익그래프·브리핑 | 한 단계만 성공했는데 완료로 표시하거나 서로 다른 버전의 상태를 읽는가? |
| 장애·자원 | GAS 6분 제한, ScriptLock, 시트 쓰기, 계정별 트리거, API 제한, 큐 크기, 자정 | 타임아웃·부분 완료·데이터 쓰기 후 상태 쓰기 실패 시 복구 가능성이 남는가? |

**사전 리뷰 통과 조건:** (1) 변경 전 실패 사례 재현, (2) 기존 기능의 대표 회귀, (3) 핵심 생산 함수 내부의 부작용까지 검증한 동작 테스트, (4) 예상 신규 P1/P2의 반례 검사, (5) CI 실제 실행·결과 확인, (6) 운영 미검증 사항 분리. 해당 없음은 근거를 기록한다.

최종 Codex 리뷰에서 구조적 결함이 발견되면 지적된 줄만 수정하지 않는다. 같은 공유 상태·실행 순서·데이터 원천을 쓰는 모든 경로를 조사하고 **왜 자체검토가 놓쳤는지**를 회귀 테스트와 영향 매트릭스에 반영한다. 같은 유형의 반복 지적은 설계/상태 모델 재검토로 승격한다.

## 3. 자동화 및 금융 데이터의 필수 불변조건

- **단일 소유권:** 공유 시트·Snapshot·가격이력·NAV에 대한 서로 충돌하는 쓰기 작업은 동시 수행되지 않는다. 조회/lease 획득/상태 저장은 경합 없는 원자 구역으로 묶는다.
- **진행성:** BUSY·SKIPPED·차단·시간초과 시 실행이 소멸하지 않으며, 조건 해제 후 후속 실행 또는 명시적 보류 대기열에 남는다. 재시도 기회가 유한하거나 외부 서비스가 지속 장애이면 회복 보장이 아닌 명시적 실패·경보로 전환한다.
- **시도 수명:** 작업 시작 전의 충돌/차단은 실제 실패 시도 횟수로 차감하지 않는다. 시작된 시도·트리거 UID·run ID·token의 연결을 유지하며 성공 후 예약은 완료/무효화한다.
- **멱등성:** 동일 계좌·날짜·종목·작업 유형의 재실행으로 행/금액이 중복 누적되지 않는다. 이미 확정된 원천값을 출처 불명 대체값으로 덮지 않는다.
- **날짜 경계:** 자정·휴장일·장전/장후·초 단위 충돌·stale lease 만료에도 실제 실행 소유권과 대상 거래일을 구분한다.
- **부분 완료:** PRICE 성공·FUND 실패 및 반대 조합을 구분한다. 실패가 완료로 보고되거나 성공 값이 실패로 덮이지 않는다.
- **운영 데이터:** 과거 수량 변동·펀드 기준가 공백·KRX 0건·해외장 날짜 차이에 대해 가격이력/평가금액/Snapshot 연결 정합성을 유지한다.
- **자원 제한:** GAS 실행 제한, ScriptLock 대기, 트리거 한도, API 조회 제한, 시간 예산, 전체 작업 누적 시간을 함께 고려한다.

## 4. 테스트 설계: 코드 존재 여부가 아닌 실제 동작

- 단순 정규식·문자열 포함·스냅샷 형태 테스트는 보조 확인에만 사용한다. 중요 조건은 **실제 생산 함수를 호출**하는 자동 테스트로 검증한다.
- 프로덕션 로직을 그대로 복사한 가짜 함수와 비교하지 않는다. 독립적인 단순 상태 모델 또는 명시적 불변조건을 오라클로 쓴다.
- 결정적 가상 시각/LockService/ScriptApp/PropertiesService/시트 모의 객체를 제공해 다음 전이를 검증한다:
  - 정상 마감, 부분 실패, 외부 API 무응답·0건, 잠금 충돌, 중복 트리거, 서로 다른 사용자 계정;
  - 19:00 정규 마감 ↔ 20:30 watchdog ↔ 22:10 백필 ↔ deferred NAV ↔ 수동 실행;
  - 시도 1·2·3 및 실행 중 예약 교체, GAS hard kill, 7분/15분 lease 만료, KST 자정·휴장일 경계;
  - 원본 수량 소급 수정, 누락 NAV 전일 이월 정책, 이미 존재하는 Snapshot, 재실행 중 일부 단계 실패.
- 순서 생성/상태 모델 테스트를 사용하고 실패한 **seed·최소 재현 순서**를 저장하여 CI에서 계속 재생한다. 기본 PR 검사에는 작고 결정적인 시드 집합을, 확장 탐색은 별도 실행에 둔다.
- 과거 P1/P2마다 재현 검사 추가 후 오류 유발 코드 변경(잠금 검사 제거, 횟수 선증가 등)을 **의도적으로 주입**해 테스트가 실패하는지 대표 변이 테스트를 한다. 변이 검사 범위는 변경한 핵심 조건에 집중한다.
- 기존 정상 사례에 대한 골든 데이터/계산 결과 비교를 병행한다. 기준 자료는 합성 또는 익명화하고 실계좌·토큰·개인정보를 CI 로그/fixture에 포함하지 않는다.

## 5. 리뷰 반복 최소화 절차

1. 기존 지적을 `신규/기존 미해결/해결됨/outdated/재현 불가`로 분류한다. 리뷰의 심각도 표기만 믿지 말고 코드와 재현 근거로 판단한다.
2. 사전 검토는 최소 **호출 경로 / 상태·잠금·시간 / 데이터 정합성 / 기존 기능 영향 / 테스트 실효성**의 서로 다른 관점으로 수행한다.
3. 관련 지적사항을 공통 원인별로 묶어 한 번에 해결하고, 확인된 문제마다 회귀검사를 남긴다. 단순히 리뷰 댓글대로 국소 조건문만 추가하지 않는다.
4. 최신 HEAD의 관련 CI 결과와 재현·변이 테스트 결과가 확보된 이후 Codex에 통합 리뷰를 1회 요청한다. 리뷰 결과가 오지 않았거나 사용 한도가 소진됐으면 완료라고 보고하지 않는다.
5. 최신 리뷰에서 P1/P2가 다시 발생하면 먼저 영향 분석과 테스트 누락 원인을 조사한다. **연속 2회 신규 구조적 지적**이 반복되면 재리뷰 요청을 멈추고 상태 모델/설계 경계부터 재검토한다.
6. 리뷰 반복의 목적은 코멘트 0개가 아니라 중요 결함의 미해결 0건이다. 단순 양식·취향성 제안과 실제 데이터 위험을 구분한다.

## 6. CI·머지·배포 분리

- 테스트 파일만 바꾸어도 해당 테스트를 수행하는 CI가 실제 실행되도록 `paths` 필터를 확인한다.
- `scripts/check-*.mjs` 또는 `package.json` 변경 PR에는 `quality-check.yml`이 전체 `npm run check:ci`를 실행한다. `check-ci-coverage`는 모든 검사 파일이 실제로 해당 suite의 호출 경로에 포함됐는지 검사하고, 누락 시 실패시킨다. `gas-deploy`와 `web-check`의 부분 검사 성공만으로 전체 테스트가 통과했다고 판단하지 않는다.
- 저장소 브랜치 보호에서 `quality-check / all-check-scripts`를 필수 체크로 지정해야 머지 차단까지 강제된다. CI 파일만 추가했다고 브랜치 보호가 자동 설정되는 것은 아니다.
- 체크가 `skipped`인 경우 실제 실행 성공으로 간주하지 않는다. 테스트 통과는 **최신 HEAD SHA 기준**으로 확인한다.
- PR/CI 통과, GitHub main 병합, GAS 코드 버전 증가, GAS 웹앱 배포, 시트 내 운영 데이터 정상 여부는 **서로 별개 상태**로 기록한다.
- 실제 시트 변경/과거 데이터 재생성/트리거 대량 삭제 전에 읽기 전용 진단·백업·롤백 방법·대상 기간을 확인한다. 데이터 파괴 작업을 단순 검증의 부작용으로 수행하지 않는다.
- GitHub branch protection의 필수 CI·미해결 리뷰 대화 차단은 별도 설정 확인이 필요하다. 문서에 적었다고 자동 강제되는 것은 아니다.

## 7. 리뷰 결과 보고에 필요한 최소 증거

- PR / 기준 SHA / 변경 파일 및 범위
- 문제의 **실제 원인**, 영향 범위, 수정 후 달라지는 상태 전이
- 수정 전 실패 재현 / 수정 후 통과 / 대표 변이 테스트의 실패 / 기존 계산 회귀 결과
- 실행한 CI 이름과 **실제 수행 여부**(통과·실패·스킵·미실행)
- Codex 최신 HEAD 리뷰 상태 및 남은 중요 지적
- `검증 완료`와 `운영 미검증`의 명확한 구분, 머지/배포/데이터 수정 여부

## 8. 결함 학습 기록

- P1/P2는 ‘왜 코드 검토에서 놓쳤는가’를 `시나리오 누락/호출 경로 누락/잘못된 오라클/CI 미실행/운영 격차/설계 문제`로 기록한다.
- 같은 유형의 지적이 재등장하면 새로운 소스 패치보다 검사 체계·불변조건·테스트 오라클을 먼저 고친다.
- 월별로 리뷰 후 신규 중요 결함 건수, 재발 건수, 실운영 누락/복구 시간, 테스트 미실행 비율을 추적하되 **임의의 개선율을 약속하지 않는다**.
