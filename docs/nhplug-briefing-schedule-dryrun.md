## 검증 대상 일정 (Asia/Seoul)

| 유형 | 목표(KST) | 보완 시도 | 최종 시각(미포함) | 미래 적용 시 GitHub Actions cron(UTC) |
|---|---|---|---|---|
| MORNING | 07:30 | 08:00 | 08:10 | 목표: `30 22 * * 0-4`, 보완: `0 23 * * 0-4` |
| CLOSE | 16:00 | 16:05 | 16:10 | 목표: `0 7 * * 1-5`, 보완: `5 7 * * 1-5` |

- **현재 main 운영:** 장전 07:40 및 08:00 보완. 07:30 예약은 아직 적용하지 않았습니다. 16:00 텔레그램 자동 발송도 운영에 존재하지 않습니다.
- KST 날짜(특히 UTC 전날 22:30과 당일 KST 07:30)의 일치, 2026년 GAS에서 확인되는 KRX 개장일 여부, 늦은 예약 실행, 08:10/16:10 이후 차단을 검사합니다. 2026년 이외에는 거래소 휴장일 미확인 시 안전하게 차단합니다.
- Github cron은 시작을 *요청*하는 시각입니다. 실행 지연이 가능하므로 사용자가 **정확히 07:30/16:00에 수신**한다고 보장하지 않습니다.
- 장전 및 마감은 서로 다른 날짜별 claim 키를 가집니다. 실제 구현 시 두 작업의 claim 원자성·독립 concurrency group을 별도로 증명해야 합니다.

## 전송 안전 계약 (모의 동작)

1. 한 종류의 브리핑에 대해 **동시에 하나의 실행자만** 메시지 생성과 claim 조회·업로드를 수행할 수 있어야 합니다. (GitHub Actions concurrency)
2. 아직 해당 날짜/유형의 claim이 **확실히 없고**, 원천으로부터 안전한 발송 문안이 검증된 경우에만 선점 준비가 가능합니다.
3. claim 업로드·readback 성공을 확인하기 **전**에는 전송하지 않습니다. claim 결과 불확실 또는 서버 에러는 UNKNOWN 상태로 남기고 후속 예약에서 자동 재전송하지 않습니다.
4. claim 성공 후 전송 결과가 모호해도 새 메시지를 보내지 않습니다. 오발송 중복 방지를 위해 at-most-once를 우선하며, 이 방식은 **발송 누락 가능성을 남깁니다**. 운영에서는 해당 상태를 경보·수동 확인해야 합니다.
5. 전송 중복 보호는 전체 브리핑 유형이 아닌 (종류, KST 거래일) 단위입니다. 장전과 장마감은 같은 날 각각 1회 가능하도록 분리합니다.
6. 해당 거래일 자료가 미확보된 경우에는 claim 없이 보완 예약을 허용하는 **모의 입력 정책**입니다. 실제 운영에서 '미확보' 문구를 보내는 것과 발송을 건너뛰는 것 중 어느 쪽이 더 적절한지는 기존 브리핑 계약과 같이 검토해야 합니다.
7. GitHub Run attempt >1은 재발송하지 않습니다.
